칼로리카운터 Oracle 배포 + GitHub Actions CI/CD

본인 칼로리카운터를 Oracle E2.1.Micro에 Docker로 띄우고, git push 한 번으로 자동 배포되는 CI/CD까지 만든다. 9주차 페이지의 "Live Demo" 버튼을 본인 데모로 연결하면 끝.

전체 흐름

오늘 작업은 두 단계로 나뉜다. STAGE 1을 먼저 끝낸 다음 STAGE 2로 넘어간다. 1을 건너뛰면 2가 디버깅 불가능.

단계하는 일끝나는 시점의 결과
STAGE 1
수동 배포		 zip 업로드 → Docker 기동 → nginx → 시트 입력 https://<ID>-demo.aiweb2026.site 접속 가능
STAGE 2
자동화		 GitHub 리포 + Secret 4개 → push 한 번 코드 수정 후 push만 하면 30초 내 사이트 갱신

오늘 만들 그림

사용자 브라우저 │ https://<본인ID>-demo.aiweb2026.site ▼ Cloudflare Universal SSL + Worker (강사 인프라) │ 시트 D 컬럼(Public IP)으로 라우팅 ▼ http 본인 Oracle E2.1.Micro · 80번 (nginx) ▼ http 본인 Docker 컨테이너 · 7860번 (Gradio)

본인이 손볼 곳은 Oracle 서버(80→7860)와 분배 시트의 본인 행 두 군데. HTTPS 인증서·DNS·Worker는 강사가 관리한다.

실습 전 손에 있어야 하는 것

  1. 9주차 숙제 — 본인 OCI 인스턴스 RUNNING + Public IP 확보
  2. 9주차에 받은 SSH 키 파일 (~/.ssh/oracle_key)
  3. 본인 Hugging Face 토큰 (hf_로 시작, Read 권한) — 6주차에 발급받은 그대로
  4. e-class에서 받은 week10_calorie.zip
  5. 본인 GitHub 계정 (9주차에 만든 그대로)
  6. 분배 시트 본인 행 위치 (강사 공유)
OCI 가입 못 한 학생 — 시트 본인 행에 강사가 안내하는 공유 IP를 일단 입력. 이후 본인 가입 완료되면 D 컬럼만 본인 IP로 갱신하면 5분 내 자동 반영.

STAGE 1 — 수동으로 한 번 띄워 본다

zip을 직접 올려서 본인 도메인이 작동하는 것을 먼저 확인한다.

1시트에 본인 Public IP 입력

분배 시트 열기 → 본인 행에서 D 컬럼에 본인 Oracle Public IP를 입력한다. IP만 적는다 — http://나 포트 번호를 같이 적으면 라우팅이 깨진다.

컬럼의미예시
A: 이름본인 식별김아무개
B: Domain본인 서브도메인s01.aiweb2026.site
C: Page Link9주차 소개 페이지 URLs01-portfolio.pages.dev
D: Public IPOracle 데모 서버 IP (오늘 입력)168.110.127.64
왜 시트에 입력하나. 강사 Cloudflare Worker가 *.aiweb2026.site 트래픽을 받아서 시트의 매핑을 5분 캐시로 조회한다. 한 행이 두 도메인으로 풀린다. s01.aiweb2026.site는 9주차 소개 페이지(C)로, s01-demo.aiweb2026.site는 본인 Oracle origin(D)로 자동 라우팅.
체크포인트. 시트 본인 행 D 컬럼에 IP가 들어가 있다. 다른 컬럼은 건드리지 않는다.

2Oracle 서버 사전 세팅 (swap + 방화벽 + nginx)

본인 인스턴스에 SSH 접속 후 다섯 가지 사전 작업을 한다. swap 추가 → iptables 80/443 ALLOW → OCI Security List 80/443 ingress → nginx 기본 설치 → 외부 도달 검증.

왜 nginx를 Docker보다 먼저 까나. 80번 외부 도달 검증을 실제로 끝내려면 80번에 무언가가 응답해야 한다. nginx 기본 welcome 페이지가 가장 단순한 응답기. 이 상태로 "방화벽 두 layer + 80번 도달"을 먼저 통과시키고 다음 단계에서 Docker 컨테이너를 올린 뒤, 마지막에 nginx 설정만 calorie-counter용으로 교체한다. 거꾸로 하면 (Docker만 먼저 띄우고 80번 검증) 컨테이너가 죽었는지 방화벽이 막혔는지 분리 진단이 어렵다.

2-1. SSH 접속

# 본인 PC 터미널에서 (PowerShell, macOS Terminal, Linux 다 동일)
ssh -i ~/.ssh/oracle_key ubuntu@<본인_Public_IP>

# Windows에서 키 경로가 다르면:
ssh -i C:\Users\<이름>\.ssh\oracle_key ubuntu@<본인_Public_IP>
접속 안 됨
  • Permissions 0644 ... too open → chmod 600 ~/.ssh/oracle_key 후 재시도
  • Connection refused → OCI Console에서 인스턴스 RUNNING 확인. STOPPED면 Start
  • Connection timed out → Security List 22번 막힘 (보통 9주차에 풀어둔 상태)

2-2. swap 2GB 설정 (1GB RAM 보강)

# Oracle 서버에서
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 검증 — Swap 줄이 2.0Gi로 나와야 정상
free -h
왜 swap을 만드나. Always Free E2.1.Micro는 RAM 1GB. Docker 첫 빌드 때 pip install이 메모리를 다 잡아먹어 OOM(Out Of Memory)으로 죽는다. swap 2GB가 있으면 빌드가 끝까지 간다.

2-3. iptables 80/443 ALLOW (REJECT 위에 끼워넣기)

OCI Ubuntu의 iptables INPUT 체인 마지막 즈음에 REJECT all -- ... reject-with icmp-host-prohibited가 박혀 있다. ALLOW를 그 뒤에 붙이면 위쪽 REJECT가 먼저 매칭되어 막힌다. REJECT 줄 바로 위 자리에 INSERT해야 한다.

# 현재 룰 확인 (REJECT 라인 번호 파악)
sudo iptables -L INPUT --line-numbers

# 출력 예 (라인 번호는 본인 환경 기준):
# 1    ACCEPT  ... state RELATED,ESTABLISHED
# 2    ACCEPT  ... icmp
# 3    ACCEPT  ... lo
# 4    ACCEPT  ... state NEW tcp dpt:22
# 5    REJECT  all -- ... reject-with icmp-host-prohibited

# REJECT가 5번이면 그 자리(5)에 INSERT — 기존 5번은 6번으로 밀림
sudo iptables -I INPUT 5 -p tcp --dport 80  -j ACCEPT
sudo iptables -I INPUT 5 -p tcp --dport 443 -j ACCEPT

# 영구 저장 (재부팅 시 유지)
sudo apt install -y iptables-persistent
sudo netfilter-persistent save

# 다시 확인 — 80/443 ACCEPT가 REJECT 위에 보여야 정상
sudo iptables -L INPUT --line-numbers | head -10
잘못 넣었을 때 되돌리기. -I 대신 -A로 추가했거나 라인 번호를 잘못 줘서 ALLOW가 REJECT 아래에 들어간 경우, 해당 룰만 골라서 지우고 다시 INSERT한다. 
# 현재 룰 + 라인 번호 다시 확인
sudo iptables -L INPUT --line-numbers

# 잘못 들어간 줄을 라인 번호로 삭제 (예: 80번이 7번 라인에 있다면)
sudo iptables -D INPUT 7

# 또는 룰 내용으로 직접 삭제 (라인 번호 셀 필요 없음)
sudo iptables -D INPUT -p tcp --dport 80  -j ACCEPT
sudo iptables -D INPUT -p tcp --dport 443 -j ACCEPT

# 삭제 후 § 2-3 절차로 REJECT 위 자리에 다시 INSERT
# 마지막에 영구 저장 다시 한 번
sudo netfilter-persistent save
-D는 delete. 라인 번호로 지우면 한 줄 지울 때마다 아래 번호가 한 칸씩 당겨지니, 여러 줄 지울 땐 아래쪽부터 지우거나 매번 -L --line-numbers로 다시 확인.

2-4. OCI Console — Security List에 80/443 ingress 추가

iptables가 풀려도 OCI 가상 네트워크(VCN) Security List가 막혀있으면 외부에서 안 닿는다. 두 layer 모두 풀어줘야 외부에서 접속 가능.

① 인스턴스 → Networking 탭 → Subnet 링크 클릭

cloud.oracle.com › Compute › Instances › 본인 인스턴스 › Networking 탭

인스턴스 상세 페이지에서 Networking 탭 클릭 → 하단 Subnet 줄의 파란색 링크(public subnet-vcn-main 등) 클릭

② Subnet → Security 탭 → Default Security List 클릭

Subnet › Security 탭 › Security Lists

Subnet 페이지에서 상단 Security 탭 → 하단 표의 Default Security List for vcn-main 링크 클릭

③ Default Security List → Add Ingress Rules 버튼 클릭

Default Security List › Security rules › Add Ingress Rules 버튼

기본 등록된 Ingress 룰(SSH 22, ICMP 등)이 보이는 표 위쪽의 Add Ingress Rules 버튼 클릭. 표 안에 80·443 룰이 이미 있으면 추가할 필요 없음 — 다음 단계 건너뛰기.

④ Add Ingress Rules 폼에 80번·443번 한 번에 등록

Add Ingress Rules › Ingress Rule 1 (포트 80) › + Another Ingress Rule › Ingress Rule 2 (포트 443)

우하단 + Another Ingress Rule 버튼을 한 번 눌러 룰 두 개를 한 화면에 만들고, 각각 80과 443을 입력한 뒤 맨 아래 Add Ingress Rules로 저장

각 룰에 입력할 값:

필드값
Stateless체크 안 함
Source TypeCIDR
Source CIDR0.0.0.0/0
IP ProtocolTCP
Destination Port RangeIngress Rule 1은 80, Ingress Rule 2는 443

저장 후 Security rules 표로 돌아가서 TCP 80과 TCP 443 두 줄이 추가된 것을 확인한다.

2-5. nginx 기본 설치 (80번에 응답기 두기)

# Oracle 서버 SSH 세션에서
sudo apt update
sudo apt install -y nginx

# 자동으로 service 기동됨 — 상태 확인
sudo systemctl status nginx --no-pager | head -5
# active (running) 줄이 보여야 정상

# 서버 자기 자신에게 nginx default 응답 확인
curl -I http://127.0.0.1
# HTTP/1.1 200 OK
# Server: nginx/...

지금은 nginx 기본 welcome 페이지만 떠있는 상태. 칼로리카운터용 reverse proxy 설정은 § 4에서 Docker 컨테이너가 7860에 떠있는 걸 확인한 뒤에 교체한다.

2-6. 검증 — 본인 PC에서 80번 도달 + 브라우저 확인

방화벽 두 layer(iptables + OCI Security List)가 모두 풀려야 본인 PC에서 서버 80번까지 도달한다. nginx가 떠있으니 응답까지 확인 가능.

# 본인 PC 터미널에서 (서버 SSH 세션 아님)

# Windows PowerShell
Test-NetConnection -ComputerName <본인_Public_IP> -Port 80

# macOS / Linux
nc -zv <본인_Public_IP> 80

그 다음 본인 PC 브라우저에서 http://<본인_Public_IP>로 접속 → "Welcome to nginx!" 페이지가 떠야 한다.

체크포인트. ① 터미널에서 TcpTestSucceeded : True (Windows) 또는 Connection succeeded (macOS/Linux). ② 브라우저에서 nginx welcome 페이지 표시. 둘 중 하나라도 실패면:
  • Connection refused → 서버에서 sudo systemctl status nginx 다시 확인
  • Connection timed out → § 2-3 iptables와 § 2-4 Security List 다시 확인

3Docker 설치 + 칼로리카운터 zip 배포

3-1. Docker 설치 — Oracle 서버에 설치한다 (본인 PC 아님)

어디서 실행하는지 헷갈리지 말 것. 이 단계의 모든 명령은 Oracle 서버에 SSH로 접속한 상태에서 실행한다. 본인 PC에 Docker Desktop을 깔라는 게 아니다. 본인 PC에는 아무것도 설치할 필요 없다.
터미널 프롬프트가 ubuntu@<본인_Public_IP>:~$ 형태면 서버 안. %나 PS> 형태면 본인 PC — 다시 ssh -i ~/.ssh/oracle_key ubuntu@<본인_Public_IP>로 들어간다. 
# Oracle 서버 SSH 세션 안에서만 실행
# (프롬프트가 ubuntu@... 인지 다시 한 번 확인)

# Docker 공식 설치 스크립트
curl -fsSL https://get.docker.com | sudo sh

# ubuntu 사용자가 sudo 없이 docker 명령 쓸 수 있게
sudo usermod -aG docker $USER

# 그룹 즉시 적용 (재로그인 안 해도 됨)
newgrp docker

# 검증
docker --version
docker compose version
왜 본인 PC가 아니라 서버에 까나. 칼로리카운터는 학기 끝나도 24시간 서비스 중인 사이트가 되어야 한다. 본인 PC에 띄우면 PC 끄는 순간 사이트도 죽는다. 그래서 항상 켜져 있는 Oracle 서버에 컨테이너를 둔다. 본인 PC는 코드만 짜고 git push만 하면 끝 — Docker는 서버에서만 돈다.

3-2. zip 업로드 — 본인 PC에서 실행

e-class에서 week10_calorie.zip을 본인 PC로 다운로드 후, 본인 PC 터미널에서 Oracle 서버로 업로드한다. 여기는 서버 SSH 세션이 아니라 본인 PC 터미널. 새 터미널 창을 하나 더 열어 PC용 작업을 한다.

# 본인 PC에서 (서버 SSH 세션이 아니라 본인 PC 터미널)

# macOS / Linux
scp -i ~/.ssh/oracle_key ~/Downloads/week10_calorie.zip ubuntu@<본인_Public_IP>:~/

# Windows PowerShell
scp -i $env:USERPROFILE\.ssh\oracle_key `
    $env:USERPROFILE\Downloads\week10_calorie.zip `
    ubuntu@<본인_Public_IP>:~/

3-4. .env 작성 — HF_TOKEN 입력

vi 최소 사용법. 이번 수업에서 텍스트 편집은 vi로 한다.
  • 편집 시작: i 키 누르면 좌하단에 -- INSERT -- 표시
  • 편집 종료: Esc 키 (insert 모드 빠져나옴)
  • 저장 + 종료: :wq 입력 후 Enter
  • 저장 안 하고 종료: :q! 입력 후 Enter
cd ~/calorie
cp .env.example .env
vi .env

.env 파일 내용을 다음 한 줄로 만든다 (따옴표 없이). i 누르고 입력 → Esc → :wq:

HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxxxxxx

9주차에 발급받은 본인 Hugging Face Read 토큰 그대로. 새로 발급할 필요 없다. 토큰이 없거나 잃어버린 학생은 huggingface.co/settings/tokens에서 새로 발급(Create new token → Read 권한 선택).

# 비밀값이니 권한 600 (소유자만 읽기·쓰기)
chmod 600 .env
ls -la .env
# -rw------- 1 ubuntu ubuntu ... .env
HF_TOKEN은 절대 GitHub에 push 금지. zip에 동봉된 .gitignore에 .env가 차단되어 있지만, 직접 GitHub에 올릴 때 한 번 더 cat .gitignore | grep .env로 확인.

3-5. 첫 컨테이너 기동 (3~5분)

cd ~/calorie
docker compose up -d --build

첫 빌드는 베이스 이미지 다운로드 + pip install로 몇 분 걸린다. 두 번째부터는 캐시 덕분에 훨씬 빠르다.

3-6. 작동 확인

# 컨테이너 상태
docker compose ps
# NAME             STATUS         PORTS
# calorie-counter  Up 30 seconds  0.0.0.0:7860->7860/tcp

# 실시간 로그
docker compose logs -f
# "Running on local URL: http://0.0.0.0:7860" 보이면 OK
# Ctrl+C로 빠져나옴

# 서버 자기 자신에게 응답 확인
curl -I http://127.0.0.1:7860
# HTTP/1.1 200 OK
OOM으로 빌드가 죽음 → § 2-2 swap 누락. free -h로 swap 2.0Gi 확인 후 docker compose up -d --build 재시도.
컨테이너 Up 됐다가 곧 Exited → docker compose logs에서 HF_TOKEN 401 또는 모델 로드 실패 확인.
체크포인트. curl -I http://127.0.0.1:7860이 HTTP/1.1 200 OK를 반환한다. 외부 접속은 아직 안 된다 — 다음 단계 nginx에서 80→7860 reverse proxy를 깐다.

4nginx 설정 교체 + 도메인 접속 검증

§ 2-5에서 깐 nginx는 default welcome 페이지를 띄우는 상태다. 이걸 calorie-counter용 reverse proxy(80 → 7860) 설정으로 교체한다.

4-1. zip 동봉 설정 적용 + 본인 ID 치환

5-3. Secret 4개 등록

GitHub Actions가 본인 Oracle 서버에 SSH로 들어가려면 민감한 값 4개가 필요하다. 이걸 GitHub의 Secret 저장소에 넣으면 워크플로우 실행 시 자동으로 환경변수로 주입된다.

github.com/<본인>/my-calorie-counter › Settings 탭 › 좌측 Security 영역 › Secrets and variables › Actions › New repository secret

Name과 Secret 값을 차례로 4번 입력한다 (한 번에 한 개씩).

이름값
SSH_HOST본인 Oracle Public IP (예: 168.110.127.64)
SSH_USERubuntu
SSH_KEY ~/.ssh/oracle_key 파일 전체 내용 (개행 포함, -----BEGIN OPENSSH PRIVATE KEY-----부터 -----END OPENSSH PRIVATE KEY-----까지 통째로)
HF_TOKEN본인 Hugging Face 토큰 (hf_로 시작)

4개 Secret 모두 등록한 직후의 모습. 값은 보이지 않고 이름만 보이는 게 정상.

SSH_KEY CRLF 함정 (Windows). Windows에서 키 파일 내용을 클립보드 복붙하면 줄바꿈이 CRLF(\r\n)로 들어가서 SSH가 거부한다.
PowerShell에서 권장 방법: 
Get-Content $env:USERPROFILE\.ssh\oracle_key -Raw | Set-Clipboard
위 명령으로 클립보드에 복사한 뒤 GitHub Secret 입력란에 붙여넣기. 또는 VS Code로 키 파일을 연 다음 우하단의 줄바꿈 표시가 LF인지 확인 후 전체 선택 → 복사 → 붙여넣기.

5-4. deploy.yml 한 번 훑어보기

zip 안 .github/workflows/deploy.yml이 자동 배포 정의 파일. 핵심만 보면:

on:
  push:
    branches: [main]              # main에 push하면 트리거
  workflow_dispatch:               # 수동 트리거 버튼

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Oracle 서버에 SSH로 배포
        uses: appleboy/ssh-action@v1
        env:
          REPO_URL: ${{ github.server_url }}/${{ github.repository }}.git
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_KEY }}
          envs: REPO_URL
          script: |
            set -e
            cd /home/ubuntu/calorie
            # 첫 배포라 .git이 없으면 자동 초기화
            if [ ! -d .git ]; then
              git init
              git remote add origin "$REPO_URL"
            fi
            git fetch origin main
            git reset --hard origin/main
            docker compose up -d --build
첫 배포의 자동 초기화. STAGE 1에서 zip을 풀어둔 ~/calorie는 git 리포가 아니다. 워크플로우가 .git이 없으면 자동으로 git init + git remote add를 실행해 다음 git fetch가 동작하도록 만든다. 본인이 SSH 접속해서 따로 손댈 필요 없다.
체크포인트. 본인 리포 Settings → Secrets에 SSH_HOST, SSH_USER, SSH_KEY, HF_TOKEN 4개 모두 등록되어 있다.

옵션 · 9주차 정정 — Pages와 Workers는 사실상 한 제품으로 통합됐다.
9주차에서는 "정적 = Cloudflare Pages, 서버리스 = Cloudflare Workers"로 둘을 별개 제품처럼 설명했다. 2026년 5월 현재 Cloudflare는 Pages를 유지보수 모드로 두고 신규 프로젝트는 Workers의 Static Assets binding으로 통합하도록 안내한다. 정적 파일과 라우팅 코드를 한 프로젝트에 같이 두고 wrangler deploy 한 번에 배포하는 방식.
  • 강사 인프라(aiweb2026-hub)도 이미 Workers 단일 구조다 — wrangler.toml의 [assets] 블록에서 ./public을 정적으로 서빙하고, src/index.js Worker가 *-demo.aiweb2026.site 트래픽을 시트 매핑 기반으로 라우팅한다.
  • 오늘 본인 9주차 페이지는 그대로 Pages에 둬도 작동하지만, 학기 종료 후 본인 인프라로 옮길 땐 Workers Static Assets로 마이그레이션하는 편이 향후 기능 확장(API·세션·KV·D1)이 쉽다.
  • 공식: developers.cloudflare.com/workers/static-assets — Pages에서 Workers로 마이그레이션 가이드 포함.
오늘 실습은 9주차에 만든 Pages 프로젝트를 그대로 쓴다. 정정은 알아두기만 하면 된다.

다른 언어로 만들고 싶다면
