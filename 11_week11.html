적격성 체크리스트는 contents.md에 있다

여기 html에 복제하지 않는 이유 — 항목은 contents.md가 단일 출처. 두 곳에 두면 한 쪽 갱신 시 다른 쪽이 어긋난다.

3. 1인 1 contents.md 작성 (45분)

3-1. demo_intro_template 폴더 → 9주차 리포에 복사

§ 0의 demo_intro_template/ 폴더 안에 4개 파일이 들어있다.

demo_intro_template/
├── contents.md     ← 학생이 채우는 본체 (신규)
├── index.html      ← 9주차 페이지 갱신본 (덮어쓰기)
├── style.css       ← contents.md 렌더 영역 스타일 (덮어쓰기)
└── README.md       ← 작성 가이드 (먼저 1회 정독)
index.html · style.css 덮어쓰기 필수. 본인 9주차 리포(<id>-aiweb2026)에 이미 있는 index.html·style.css는 9주차 시점의 OLD 버전이라 contents.md를 못 읽는다. 폴더의 새 파일로 덮어써야 본인 페이지에 contents가 렌더된다. 갱신본은 <script type="module" src="https://cdn.jsdelivr.net/npm/zero-md@3?register"></script> + <zero-md src="contents.md" no-shadow></zero-md>가 추가돼 있다.

복사·덮어쓰기 흐름:

# 본인 9주차 리포 작업 디렉터리에서 (예: ~/repos/<id>-aiweb2026)

# 1) 기존 index.html / style.css 백업 (9주차 시점 본인 커스터마이즈 보존용)
mv index.html index.html.bak
mv style.css style.css.bak

# 2) 새 파일 복사
cp <수업자료>/week11/demo_intro_template/contents.md .
cp <수업자료>/week11/demo_intro_template/index.html .
cp <수업자료>/week11/demo_intro_template/style.css .

# Windows PowerShell 예
# Rename-Item index.html index.html.bak
# Rename-Item style.css style.css.bak
# Copy-Item <수업자료>\week11\demo_intro_template\contents.md .
# Copy-Item <수업자료>\week11\demo_intro_template\index.html .
# Copy-Item <수업자료>\week11\demo_intro_template\style.css .

백업본(.bak)은 본인이 9주차에 커스터마이즈했던 부분(헤더 문구, 색상, 카드 등)을 새 파일에 옮겨 붙일 때 참조용. 다 옮겼으면 삭제. 헷갈리지 않게 commit 전에는 .bak 파일을 staging에서 빼거나 .gitignore에 *.bak 추가.

contents.md 파일명은 반드시 그대로 — 9주차 페이지가 이 이름으로 자동 렌더한다.

3-2. contents.md 작성 흐름

처음 15분:  트랙 선택 + 인프라 트랙 표시 + 문제 + 사용자 + 핵심 기능 3개
다음 15분:  입력/출력 흐름 + 기술 스택 + 데이터 출처
마지막 15분: 완료 조건 + 본인 점검 체크리스트

안의 [대괄호 placeholder]를 모두 본인 값으로 교체. 적격성 체크리스트 8개 [ ] → [x]로 자가 점검.

contents.md는 .md 파일이라 수시로 수정한다. 한 번 작성하고 끝나는 문서가 아님. 강사 댓글 받으면 → 보완 → push → 본인 사이트 새로고침. 12~13주차 구현하면서 기능·기술 스택·완료 조건이 바뀌면 그때마다 같이 갱신. app.py·Dockerfile이 살아있는 것처럼 contents.md도 살아있는 문서다.

3-3. GitHub에서 contents.md 편집하는 2가지 방법

본인 리포에 push한 뒤에도 GitHub 웹에서 바로 수정할 수 있다. 로컬 git pull/commit/push 안 거쳐도 됨.

방법URL특징
일반 GitHub https://github.com/<username>/<repo> 파일 클릭 → 연필 아이콘 → 인라인 편집 → Commit. 빠른 한 줄 수정용.
VS Code Web (github.dev) https://github.dev/<username>/<repo> 리포 페이지에서 키 .(마침표) 한 번 눌러도 같은 화면. 풀 VS Code 인터페이스 — 여러 파일 동시 편집, 검색, 미리보기. push까지 브라우저 한 번에 처리. 설치 불필요.

github.dev는 본인 PC에 git/VS Code 안 깔려 있어도 동작. 학교 PC·태블릿에서 contents.md 손볼 때 편하다. 변경은 자동 저장 안 되고 좌측 Source Control 패널에서 commit·push 명시적으로 눌러야 반영.

3-4. 사용할 모델 탐색 (HF Hub)

주로 트랙 B 학생에게 해당. 트랙 A/C 학생은 분류기·임베딩 등 보조 모델 고를 때 참고. huggingface.co/models에서 본인 데모에 쓸 모델을 찾는다.

필터 + 정렬 흐름

1 좌측 사이드바(Tasks · Languages · Libraries 필터)   2 본문 모델 리스트   3 상단 검색·정렬 영역

번호위치이 수업에서 할 일
1좌측 사이드바Tasks에서 본인 데모 작업 선택 → Languages에서 Korean → Libraries는 Transformers
2본문 모델 리스트다운로드 수·하트 수가 높은 것 위주로 후보 추리기
3상단 검색·정렬정렬을 Most Downloads 또는 Trending으로 변경

모델 카드에서 확인할 4가지

예시: nateraw/food 모델 카드. 1 탭 (Model card · Files and versions · Training metrics · Community)   2 Inference Providers 위젯 (브라우저에서 즉시 테스트)   3 Deploy · Use this model 버튼

항목어디서왜
모델 크기 1 탭에서 Files and versions 클릭 → *.safetensors / pytorch_model.bin 용량 HF 무료 16GB RAM. 체크리스트 기준 1GB 이하 권장
라이선스 모델 카드 상단의 라이선스 태그 (예: license: apache-2.0) MIT·Apache 2.0·CC는 OK. Llama·일부 모델은 상용 제한 — 확인 필요
Intended use / Limitations 본문 README (Model description · Intended uses & limitations 섹션) 본인 데모 도메인 적합 여부, 알려진 편향·실패 케이스
예제 코드 3 우측 상단 Use this model 버튼 → pipeline snippet 본인 app.py에 그대로 붙여 첫 동작 확인

최소 사용 예 (Transformers pipeline)

from transformers import pipeline

# 예: 한국어 감정 분석
clf = pipeline("text-classification", model="/")
result = clf("이 영화 재밌었다")
# [{'label': 'POSITIVE', 'score': 0.98}]

<id>/<repo>는 본인이 고른 모델의 HF 경로. 예: monologg/koelectra-small-finetuned-nsmc.

4. 본인 페이지 반영 (15분)

4-1. contents.md 본인 페이지에 반영

3-1에서 덮어쓴 index.html은 같은 폴더의 contents.md를 zero-md로 인라인 렌더한다.

git add contents.md index.html style.css

로컬에서 확인하려면 http 서버 띄울 것. index.html을 탐색기 더블클릭으로 열면 브라우저가 보안 정책상 같은 폴더의 contents.md를 못 읽는다. 결과: 제안서 영역이 빈 박스로 보임. 
cd <본인 9주차 리포>
python -m http.server 8000
# 브라우저: http://localhost:8000

4-2. index.html placeholder 교체 (본인 프로젝트로)

덮어쓴 새 index.html은 hero + 데모 카드 안에 [본인 프로젝트 이름]·[프로젝트가 무엇을 하는지 한 줄로]·<본인 GitHub username>/<본인 프로젝트 리포> 같은 placeholder가 박혀있다. 본인 기말 프로젝트 값으로 교체.

위치교체할 값
<title>본인 프로젝트 이름 + 본인 익명 ID
hero <h1> + .tagline프로젝트 이름 + 한 줄 요약
데모 카드 screenshot.png본인 데모 화면 캡쳐. 아직 없으면 placeholder 이미지 유지 (구현 후 교체)
Live Demo <a href>현 시점에는 "#" 유지 + Coming soon 뱃지. § 5-6 또는 13주차에 본인 Live URL로 교체
Source on GitHub <a href>본인 기말 프로젝트 리포 URL (HF 트랙은 § 5-1에서 만든 신규 리포, OCI 트랙은 10주차 칼로리카운터 리포 또는 신규 리포)

본문은 <zero-md src="contents.md">가 contents.md를 자동 렌더하므로 손댈 곳 없음. contents.md만 갱신하면 본인 페이지가 따라온다.

git add index.html
git commit -m "feat: 9주차 페이지 placeholder를 기말 프로젝트로 교체"
git push origin main

Live Demo URL 확정 시점: HF 트랙은 § 5-6 (오늘 안), OCI 트랙은 13주차 본인 기말 배포 완료 시. URL 패턴 — OCI는 <id>-demo.aiweb2026.site/final, HF는 https://<id>-final-<slug>.hf.space (전체화면 직접 앱 URL).

5. HF Spaces 폴백 인프라 구축 (45분)

OCI 미완 학생 필수. OCI 완료 학생은 그대로 본인 사이트 사용. 학습용으로 따라해도 OK (학기 후 카드 없이 유지 가능한 대안 확보).

repo 2개 구조 — GitHub이 source of truth, HF Space는 deploy target. 
[학생] → GitHub repo (코드 + Actions)
       ↓ git push origin main
   GitHub Actions (sync-to-hf.yml)
       ↓ force push
   HF Space repo (Docker 빌드 + 호스팅)
       ↓
   https://<id>-<repo>.hf.space
학생은 GitHub만 만진다. HF Space repo는 CI가 자동 동기화. HF Space에 직접 push해도 동작은 하지만 GitHub-first 채택 이유 — 9~10주차 흐름과 일관 + github.dev 편집 + Actions 로그 디버깅 + PR/Issues.

5-1. hf_starter 폴더 → 신규 GitHub 리포에 복사

§ 0의 hf_starter/ 폴더는 다음 구조다. 6주차 칼로리카운터 코드 + Dockerfile (포트 7860) + GitHub Actions sync가 모두 들어있어 본인이 직접 5-3·5-4를 작성할 필요 없다.

hf_starter/
├── app.py                              ← 6주차 칼로리카운터 (Gradio)
├── model_config.py                     ← 모델 상수 + InferenceClient
├── requirements.txt
├── Dockerfile                          ← 포트 7860 (HF Space용)
├── .env.example                        ← HF_TOKEN 자리 (로컬 테스트용)
├── .gitignore                          ← .env 차단
├── README.md                           ← 상세 가이드
└── .github/
    └── workflows/
        └── sync-to-hf.yml              ← push → HF Space 자동 sync

본인 GitHub에 신규 리포(예: {본인_리포_이름}) 생성 → clone → hf_starter/ 폴더 내용 전부 복사:

git clone https://github.com/<본인>/{본인_리포_이름}.git
cd {본인_리포_이름}

5-2. HF 계정 + Access Token

  1. huggingface.co/join 가입 (이메일·비밀번호·사용자 이름. 본인 GitHub username과 같으면 편하다)
  2. 이메일 인증 → Settings → Tokens에서 Access Token 발급
    • Token type: Write (Read 토큰은 push 불가)
    • 이름: aiweb2026-deploy 등 자유
    • 발급된 hf_... 토큰을 안전한 곳에 임시 저장. 노출 금지.

1 Token type에서 Write 선택 (Read는 push 불가)   2 Token name 입력 (aiweb2026-deploy 등)   3 Create token 클릭 → 발급된 hf_... 값 복사 후 안전한 곳에 임시 저장

토큰 노출 금지. Create token 직후 1회만 전체 값이 보인다. 화면을 떠나면 다시 못 본다. 코드·Git·Slack·DM에 절대 붙여넣지 말 것. 노출됐으면 tokens 페이지에서 즉시 Revoke.

5-4. Dockerfile 포트 확인 (이미 7860)

동봉 Dockerfile은 HF Space 기본 포트 7860으로 이미 설정돼 있다. 직접 만들지 말고 그대로 사용.

# 동봉 Dockerfile 핵심 라인
EXPOSE 7860
CMD ["python", "app.py"]   # Gradio는 7860 기본

참고: 10주차 OCI용 Dockerfile은 보통 8000번 포트(uvicorn). HF Space는 7860만 받기 때문에 동봉본은 별도 버전. nginx·docker-compose·cert/는 HF 트랙에서 사용 안 함 (HTTPS·도메인을 HF가 자동 제공).

README.md YAML frontmatter 필수. HF Space는 README.md 맨 위 YAML frontmatter를 Space 설정으로 읽는다. 없으면 "Configuration error — Missing configuration in README" 에러로 빌드 실패. hf_starter/README.md에 동봉돼 있으니 그대로 push하면 된다. 본인 프로젝트로 바꿀 때 title·emoji·colorFrom·colorTo만 교체. sdk: docker·app_port: 7860은 유지. 
---
title: Calorie Counter
emoji: 🍱
colorFrom: yellow
colorTo: red
sdk: docker
app_port: 7860
pinned: false
---

colorFrom·colorTo 허용값 8개만 가능: red·yellow·green·blue·indigo·purple·pink·gray. orange·brown 등 입력 시 HF가 push 거부.

5-5. GitHub Actions로 자동 sync

git push origin main 한 번으로 HF Space가 자동 빌드되도록 한다. 동봉 워크플로우(.github/workflows/sync-to-hf.yml)를 본인 값으로 교체 + Secret 등록.

1) GitHub Secret 등록 — 본인 GitHub 리포 → Settings → Secrets and variables → Actions → New repository secret

  • Name: HF_TOKEN
  • Value: 5-2에서 받은 hf_... 토큰

2) 워크플로우 env 본인 값으로 교체 — .github/workflows/sync-to-hf.yml 안의 HF_USER·HF_SPACE를 본인 값으로.

env:
  HF_TOKEN: ${{ secrets.HF_TOKEN }}
  HF_USER: <id>           # ← 본인 HF username
  HF_SPACE: <repo>        # ← 본인 HF Space 이름 (5-3에서 만든 Space name)

3) commit + push

git commit -am "feat: HF_USER, HF_SPACE 본인 값으로 교체"
git push origin main

GitHub 리포 → Actions 탭에서 워크플로우 녹색 확인 → 1~3분 후 HF Space URL에 본인 앱 떠 있음.

5-6. 9주차 페이지의 Live Demo 버튼 살리기

9주차 페이지의 데모 카드 버튼이 placeholder 상태일 것. 전체화면 직접 앱 URL(https://<id>-<repo>.hf.space)로 교체. Space 페이지(huggingface.co/spaces/...)는 HF 헤더·사이드바가 함께 떠서 데모 카드 링크로는 부적합 — 직접 앱 URL이 풀스크린으로 본인 앱만 보여준다.

<!-- 변경 전 -->
<a href="#" class="btn-disabled">Live Demo (Coming Week 10)</a>

<!-- 변경 후 -->
<a href="https://<id>-<repo>.hf.space" class="btn-primary" target="_blank" rel="noopener">Live Demo</a>

<id>-<repo>는 본인 HF username과 Space name을 하이픈으로 이은 형태. 예: username + calorie-counter → https://username-calorie-counter.hf.space. 정확한 URL은 Space 페이지 우상단 ⋮ → Embed this Space → Direct URL에 표시된다. class는 본인 페이지의 활성 버튼 클래스로 교체 (btn-primary·btn·button 등). push 후 Cloudflare Pages가 1~2분 안에 자동 배포.
